2 · The Double-Charge Race Condition

Root cause — three interlocking gaps

ForgeMart has two paths that both reach completeCheckout:

  • Payment webhook — dispatchPaymentWebhook fires on checkout.session.completed
  • Storefront confirm — POST /checkout/:sessionId/confirm fires when client JS reports success

Gap 1 — TOCTOU in completeCheckout (the critical bug). isHeld() is a read, not ownership transfer. Both concurrent callers pass it before either reaches orders.create() → two orders created → double charge.

Gap 2 — non-idempotent create. OrderRepository.create produced a brand-new order row on every call (its own JSDoc admitted it).

Gap 3 — external pre-acquire. The webhook called lock.acquire() before completeCheckout, so checkout only needed isHeld = true — no atomic ownership check existed.

3 · The fix — four files changed

completeCheckout — acquire, don't just read

// OLD: read-then-act (TOCTOU)
const held = await deps.lock.isHeld(sessionId)
if (!held) { return PAYMENT_NOT_LOCKED }
await deps.orders.create(session)   // ← two callers race here

// NEW: compare-and-set ownership
const won = await deps.lock.acquire(sessionId)   // exactly one wins
if (!won) {
  await deps.lock.waitUntilReleased(sessionId)   // loser waits
  const existing = await deps.orders.findBySession(sessionId)
  if (existing) return { ok: true, order: existing }  // same order
  return PAYMENT_NOT_LOCKED
}

PaymentLock — add waitUntilReleased

A waiter registry (Map of resolver callbacks per sessionId); release() drains them. The loser blocks without spinning.

OrderRepository.create — idempotent guard (defence in depth)

const existing = await this.findBySession(session.id)
if (existing) return existing   // second line of defence

dispatchPaymentWebhook — remove the pre-acquire

The webhook no longer holds the lock before calling completeCheckout — that setup is what made the old isHeld design look “safe” for the single-path case while remaining racy under concurrency.

Verification — all 20 tests pass

  • ✔ Concurrent webhook + storefront confirm → exactly 1 order, same ID to both
  • ✔ Late storefront confirm after webhook finished → idempotent create returns existing order
